# T2S 功能改进计划：多日期与多区间查询

**状态：待启动。** 后续从 main 单独开功能分支。启动开发时更新此状态。

## 用户要查什么

用户可以在一条问题里指定若干单日、若干连续区间，或者两者混用。每次查询沿用一个指标和既有的分组能力。以 2026 年 9 月 1 日、10 日、20 至 22 日的实付金额为例：

| 问法 | 确认卡与结果 |
| --- | --- |
| 一共多少 | 3 段，共 5 个不同日期。合并统计，返回一个总数 |
| 每段分别多少 | 按用户列举顺序返回 3 份结果，20 至 22 日为一份 |
| 合起来按天列 | 只在所选日期内按天分组，沿用现有分组对无记录日期的行为 |

建议未明确要求分段时采用合计，确认卡显示模式并允许切换。此项是待 review 的默认值。

## 当前限制和改动理由

当前 Plan、提示词、日期修正、确认卡和 SQL 编译器均使用一对起止日期。旧评测 B03 要求只查 1 日和 10 日，模型曾给出 1 日到 10 日。严格模式追问，实验诊断模式生成了错误确认卡。先扩展计划的表达能力，再评估模型能否正确区分“和”与“到”。

## 计划与计算口径

自然语言由 Ollama 生成结构化候选计划，表单直接提交用户选项。建议统一使用以下计划结构；模型决策外层仍携带状态、缺项和引文。

~~~json
{
  "metric": "paid",
  "periods": [
    {"first_day": "2026-09-01", "last_day": "2026-09-01"},
    {"first_day": "2026-09-10", "last_day": "2026-09-10"},
    {"first_day": "2026-09-20", "last_day": "2026-09-22"}
  ],
  "result_mode": "combined",
  "dimension": "none",
  "category": null
}
~~~

- 每段对用户均含首尾日。编译时转为左闭右开区间，例如 20 至 22 日对应时间列大于等于 20 日零点且小于 23 日零点。保留原始列表供确认、修改和分段展示。
- `combined` 在所选日期的并集上执行一次原指标。使用带括号的多个参数化范围条件，统一应用订单状态和品类筛选。重叠日期只算一次。例：同一订单在两个选中日期发了包裹，发货订单总数仍为 1。
- `per_period` 按原始区间分别聚合，用固定段编号标记各段。建议用带参数的 UNION ALL 合成一条只读查询，保留段内分组，并使用全局排序与行数限制。重叠日计入各自区间。分段结果按原始顺序展示，CSV 带日期标签。
- 引文保留给 trace 和排错。指标、日期有效性、执行授权由后端验证。多日期不能扩大库存快照支持范围。实现前核定区间数量上限，以及现行 366 天限制在多段情形下的计算口径。

## 实施顺序

下列路径均相对仓库根目录。

| 步骤 | 文件 | 交付与验证 |
| --- | --- | --- |
| 1. 计划协议与兼容 | `src/t2s/planning/models.py`、`src/t2s/sessions/models.py` | 增加区间列表和模式，兼容旧 Plan、Choice 和 Redis checkpoint。单测覆盖旧 end 是否含当天，以及新旧输入冲突 |
| 2. 验证与执行 | `src/t2s/planning/rules.py`、`src/t2s/query/compiler.py`、`src/t2s/query/executor.py` | 先用手写计划验证合计、分段、重叠、按天或月分组；保留参数绑定、只读事务、超时和整次最多 1000 行 |
| 3. 模型理解 | `src/t2s/planning/{planner,dates,decision_rules,evidence}.py`、`src/t2s/resources/prompts/policy.txt` | 更新 JSON Schema 与提示样例，覆盖单日、离散日期、混合区间、含糊表达和两种结果模式；避免单段修正逻辑覆盖多段结构 |
| 4. 多轮与确认 | `src/t2s/workflow/graph.py`、`src/t2s/sessions/service.py` | 区分追加、替换和移除，保留未修改的指标、分组和筛选；新版确认卡才能执行，所有区间只需一次批准 |
| 5. 展示与追踪 | `src/t2s/resources/web/`、`src/t2s/observability/trace.py` | 表单和追问可增删区间，确认卡展示原始区间、不同日期数与模式，结果和 CSV 标明各段。记录区间数、模式、版本和执行摘要 |
| 6. 验收 | `tests/unit/`、`tests/acceptance/`、`evals/` | 手写计划对照独立 MySQL 参考结果，再经真实 Ollama、浏览器确认、多轮修改和导出验证完整链路 |

## 验收样例

1. 同一指标分别问“1 日和 10 日”“1 日到 10 日”，确认卡和查询结果分别覆盖 2 天和 10 天。
2. 混合案例在未选中的 5 日放入一笔显眼的大额订单。1、10、20 至 22 日的合计必须准确排除它。
3. 两段相交时验证合计去重、分别统计保留交集。一个订单跨两天发货时，合计订单数为 1，分段各为 1。
4. 覆盖无记录区间、跨月、非法日期、库存非快照日。“9 月初挑几天”应追问具体日期。
5. 多轮追加、替换、移除后核对每一版计划。旧确认卡不得执行，取消零执行，重复确认不重复查询。
6. 保留旧版 B03 的历史成绩，新版 B03 要求准确确认两个单日且最终金额正确。冻结额外口语变体，分别记录计划准确性、错误确认卡、额外追问、结果正确性和未授权执行次数。模型对自然语言的理解需要实测。
